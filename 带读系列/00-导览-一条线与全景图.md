## 🧵 一条线：从零件到整机

6 篇带读**不是并列**的，而是一条**由具体到抽象、由零件到整机**的线。每篇都解决了上一篇留下的悬念：

```text
① 一个完整工具 (tool-todo)
   │  学会"定义"一个工具。悬念：register 之后，工具怎么被调用？
   ▼
② 工具注册表与管线 (core/tools)
   │  学会"五段策略管线"。悬念：这些事件/结果写到哪了？模型历史从哪来？
   ▼
③ 会话日志 (core/session)
   │  学会"唯一真相源"。悬念：谁来驱动日志的写入？
   ▼
④ 主循环 (agent-loop)  👑
   │  学会 turn/step 如何串起工具与日志。悬念：多个工具调用怎么调度？
   ▼
⑤ 工具调度器 (tool-calls)
   │  学会并发/顺序/中断保全。悬念：这一切怎么装成一个 agent？
   ▼
⑥ 组装骨架 (spine-demo + cordis.yml)
      学会"骨架 + 配置"如何装配成整机。终点。
```

## 🗺️ 全景流程图：一次请求如何流过 dsh

下图把 6 篇带读的所有机制，折叠成**一条用户消息从输入到工具执行**的完整路径。每个框旁标了它出自哪篇带读、对应哪个 `session.append` 事件。

```text
                        ┌─────────────────────────────────────────────┐
   用户消息 ──followup──▶│  ReactLoopAgent (agent-loop)   【带读④】     │
                        │  状态机: idle → running                       │
                        │  inbox: next-turn / next-step 【④·三】        │
                        └─────────────────────────────────────────────┘
                                          │  wakeDriver → kick → turn()
                                          ▼
   session.append('turn/start') ◀─── turn() 开回合  【带读④·四】
                                          │  循环 step
                                          ▼
   ┌────────────── preStep 【带读④】 ───────────────┐
   │ inbox.claim → systemPrompt.assemble            │
   │ agent/pre-step waterfall (可改写/拒绝消息)      │
   └────────────────────────────────────────────────┘
                                          │  session.append('step/start')
                                          ▼
   ┌────────────── buildRequest 【带读④·六】 ───────┐
   │ agent/request waterfall (改 provider/model)    │
   │ llm.prepareCall → request/header 落日志        │
   └────────────────────────────────────────────────┘
                                          │
                                          ▼
   session.deriveMessages() 【带读③·四】 ──▶ llm.stream(request)
                                          │  for await chunk:
                                          ▼
   session.append('assistant/chunk') ×N  【带读③】
                                          │  assembler.finish
                                          ▼
   session.append('assistant/message', {sourceEventSeqs:[chunks]})  【带读③·三】
                                          │
              ┌───────────────────────────┴───────────────────────────┐
        无 tool-call                             有 tool-call
              │                                       │
   return completed                       session.append('tool/call') ×N
              │                                       ▼
              │                       ┌── executeToolCalls 【带读⑤】 ──┐
              │                       │  按 parallel/exclusive 分组     │
              │                       │  并发派发，有序提交             │
              │                       │                                  │
              │                       │  对每个 call 走 core/tools 管线  │
              │                       │  【带读②】                       │
              │                       │   pre-execute(策略)             │
              │                       │      → guard(不变量)            │
              │                       │      → execute(超时/重试)       │
              │                       │      → post-execute(改写)       │
              │                       │      → result(观测)             │
              │                       │                                  │
              │                       │  session.append('tool/result',   │
              │                       │     {sourceEventSeqs:[call]})    │
              │                       └──────────────────────────────────┘
              │                                       │
              ▼                                       ▼
   agent/turn-stopping (serial, 可插话) ◀──── step 结束判断
              │
              ▼
   session.append('turn/end', {reason})  【带读③/④】
              │
   inbox 还有输入? ─是─▶ 继续 turn()     ─否─▶ idle，等下一条消息
```

**读图三句话**：
1. **纵向是时间**：从上到下是一次 turn 的完整生命周期；
2. **每个 `session.append` 都是带读③的"日志事件"**：整条流程的"产物"全部沉淀进唯一真相源；
3. **每个虚框都是一个可替换/可拦截的扩展点**：换 provider 改配置、加策略改监听器，**主循环本身从不需要动**。

## 🎓 毕业练习：做一个"只读代码审查"子智能体能力

用一个小而完整的项目，把 6 篇带读的知识**全部用上**。目标：给 dsh 加一个**只读的代码审查能力**，模型可以用它列出"工作区里最近改动的文件 + 简要 diff 摘要"。

### 练习要求（覆盖每篇带读）

**任务 1 — 写工具（用上 带读①）**
- 新建插件包 `tool-review`，定义工具 `review_changes`：
  - `parameters`：`{ since?: string }`（默认对比 `HEAD~1`）；
  - `output.schema`：返回 `{ files: [{ path, added, removed }], totalFiles }`（**规范值**）；
  - `output.render`：把规范值翻译成模型可读的摘要（**与规范值分离**）；
  - `presentCall` / `presentResult`：UI 卡片，**纯函数**；
  - `execute`：调 `git` 拿 diff stat（通过 `ctx.shell` 或 `ctx.subprocess`），遵守 `exec.signal`。

**任务 2 — 加一道策略（用上 带读②）**
- 再写一个插件 `review-guard`，监听 `tools/pre-execute`：当 agent 处于 "plan mode"（若有）或某个自定义环境变量打开时，把 `review_changes` 的调用**deny**，并给出原因。体会 pre-execute（策略）与 guard（不变量）的差别。

**任务 3 — 验证日志可重放（用上 带读③）**
- 跑一次让模型调用 `review_changes` 的会话；
- 用 `ctx.sessions.create(id, { seed })` 或仓库自带的 snapshot 工具**重放**该会话，检查：`tool/call` 与 `tool/result` 是否配对？`deriveMessages()` 投影出的历史是否与原会话一致？

**任务 4 — 把它挂进骨架（用上 带读⑥）**
- 在一份自定义 `cordis.yml` 里叠加你的两个插件（`--patch`），用 `dsh web --patch ./my-review.yml` 启动，确认工具在 Web UI 可见、可调用、卡片正常渲染。

**任务 5（选做，进阶） — 解释并发（用上 带读④⑤）**
- 让模型在一次回复里**同时**调用 `review_changes` 和一个已有的 `parallel` 工具。观察日志：`tool/call` 的顺序与 `tool/result` 的顺序是否一致？为什么？

### 验收清单

- [ ] 任务 1：工具能被模型调用，返回规范值，UI 卡片正确
- [ ] 任务 1：`output.render`（模型可见）与 `presentResult`（UI）确实分离，且 `presentResult` 是纯函数
- [ ] 任务 2：策略在条件满足时生效，被 deny 的调用仍形成完整 call/result 对
- [ ] 任务 3：重放后的派生消息与原会话一致（"模型可见 ⟺ 已记录"成立）
- [ ] 任务 4：配置叠加生效，无需改任何核心包
- [ ] 能用自己的话解释：为什么任务 2 不能写进 `execute`、任务 4 不需要改主循环

### 如果你卡住了

| 卡点 | 回到哪篇 |
|---|---|
| 不知道 `defineTool` 五件套怎么填 | 带读①·第四段 |
| pre-execute / guard / execute 分不清 | 带读②·第二、四段 |
| 不确定结果要不要自己写日志事件 | 带读③·第三段（表面事件） |
| 不知道工具结果怎么进模型历史 | 带读③·第四段 + 带读④·第五段 |
| 并发顺序对不上 | 带读⑤·第二段 |
| 不知道怎么把插件挂进 Web UI | 带读⑥·第三、四段 + 主手册阶段④ |
